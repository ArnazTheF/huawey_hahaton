# Ограниченный буфер наблюдений

13 ноября 2026. Реализован отдельный блок observation_memory, управляемый хостом.
Модельные facts/hypotheses/artifacts и прочие state_patch-поля не менялись.

## Что исправлено

После выполнения инструмента наблюдение автоматически сохраняется, независимо
от того, записала ли модель state_patch. Последующее read больше не обязано
удалять из контекста предыдущий короткий результат вычисления. Запись содержит
ID oN, действие/команду, фактический результат, returncode/timeout/truncated,
версию рабочей папки и консервативную отметку свежести. Модель не может изменять
этот блок через ответ. Результат автоматической проверки coding перед сдачей
тоже сохраняется, в том числе при отказе валидатора принять DONE.

Модуль baseline/observation_memory.py; подключение baseline/context.py и solver.py.
Флаги run_agent.py и scripts/experiment.py:

    --observation-memory bounded --observation-memory-chars 3000

Контроль off остаётся значением по умолчанию. Пока поддерживаются unified
state/hybrid с fixed selection без маршрутизации. Параметры памяти входят в
settings и в совместимость обучающих примеров portfolio. Старые записи
нормализуются как off, поэтому не смешиваются с новым режимом.

## Ограничения и цена

До четырёх компактных записей, приоритет двум последним командам Bash. Чтения
не могут бесконечно вытеснять обе эти команды. Самое последнее наблюдение уже
есть в latest_observation и повторно не передаётся. Дополнительный JSON-блок
ограничен 3000 символами вместе с метаданными. Это не 3000 токенов. Строки в
записях сокращаются с сохранением начала/конца и отметкой excerpted_fields.
Исходное ограничение вывода инструмента отдельно сохраняется в truncated.

При переполнении записи вытесняются; гарантии вечного хранения в контексте нет.
Полный журнал прежних tool-событий остаётся в host trace. Автоматического поиска
по вытесненным записям в этой версии нет. Семантической проверки claims, дедукции
невыполнимости или автоматического выбора правильного ответа нет.

Снимок содержит пути, права и хеши содержимого файлов/директорий. Он проверяется
после каждого реального инструмента, включая Bash, с лимитами 4096 записей,
32 MiB файлов и 0.5 секунды. Симлинки/специальные файлы не открываются.
Превышение лимита, гонка читаемого файла или ошибка чтения дают unknown.
Аудит не является атомарным снимком всей файловой системы; время, переменные
процесса и внешние зависимости не проверяются. Случайно изменившийся любой файл
помечает предыдущие результаты stale, даже если не был их зависимостью.
Bash, изменивший файлы, получает unknown для связи своего вывода с итоговой
версией. unchanged не означает, что вычисление было правильным.

## Тесты без API

79/79 прошли в read-only Docker с network none, 4 CPU, 16 GiB.
OBSERVATION_MEMORY_TEST_RESULTS.txt. Новые проверки включают:

- вычисление -> read без state_patch -> результат всё ещё доступен;
- запрет изменения наблюдений моделью, отсутствие записи невыполненных действий;
- устаревание после write и после реальной команды Bash;
- изменение содержимого при сохранённых размере и mtime;
- сохранение ошибок, таймаутов и признаков обрезки;
- границы размера при Unicode/JSON escaping, сохранение команд после множества чтений;
- unknown при неполном аудите, симлинках и специальных файлах;
- сохранение неудачной автоматической проверки coding после следующего read;
- прежние history/legacy/portfolio-контроли и разделение данных конфигураций.

## Полные API-прогоны

Два знакомых примера: snapshot_revenue и stable_toposort. Реальный API в Docker,
qwen3.8-27b-noreason, без reasoning. Каждая серия: максимум 3200; на задачу 1600,
16 шагов, output cap 900, tool output 12000, 150 секунд. Отдельные свежие копии
задач и оценщика входа; эталоны и дополнительные тесты вне контейнера агента.

| Режим | Решено | Расход | Вызовы | input tokens | output tokens |
|---|---:|---:|---:|---:|---:|
| off | 0/2 | 2650.7 | 14 | 15027 | 1148 |
| bounded | 0/2 | 2559.3 | 11 | 15253 | 1034 |

Обе серии упирались в бюджет, обрезанные ответы и ошибки JSON. Прирост качества
не подтверждён. Разница расхода по одному повтору не является доказанной
экономией. Это диагностические знакомые случаи, не независимая валидация.
После них добавлены память автоматической проверки DONE и начало/конец выдержек;
полное API-сравнение окончательной ревизии не перезапускалось. Хеши первой
ревизии сохранены в manifest.json, окончательной — в hashes_after_tests.

## Изолированная проверка через API

scripts/probe_observation_recall.py. На тех же реальных CSV программа в фиксированном
префиксе инструментов фактически вычисляет сумму, затем читает первые 500 байт
CSV. Далее выполняется один живой запрос модели: final/skip, без новых инструментов.
Правильная программа префикса задана исследователем — это проверка удержания и
использования наблюдения, НЕ оценка самостоятельного решения полной задачи.
Эталон не загружается в контейнер; сверка выполнена отдельно на хосте.

Без буфера число исчезло из контекста: модель пыталась вычислять заново и выдала
обрезанный JSON с командой. Расход 225.4. С буфером число оставалось доступным:
модель сдала final 438293, совпавшее с внешним эталоном. Расход 139.3.
Дополнительный блок: 1005 символов. Отправленные сообщения совпадают после
удаления observation_memory; model и output cap 128 также совпадают. Проверка
равенства сохранена в runs/observation-memory-v1/recall-evaluation.json.

Первая попытка bounded была остановлена ДО HTTP-вызова консервативным cold-start
оценщиком при внутреннем потолке 500. Повторён только не отправленный вариант с
потолком 900; фактический output cap обоих отправленных запросов равен 128.
Это инфраструктурное различие не изменило переданный лимит генерации или
остальные сообщения. Один ответ на вариант, без статистической значимости.

Общий фактический расход этого этапа: 5574.7 из объявленных 6400;
reasoning 0. Дополнительные API-вызовы не запущены.

## Решение

Структурная потеря наблюдения исправлена и покрыта тестами; живая изолированная
проверка показала использование восстановленного результата. Доказательств
общего улучшения баллов/цены пока нет. Поэтому новый буфер доступен флагом,
а обычный state остаётся контролем. Следующий эксперимент должен отдельно
проверять полные задачи при достаточном запасе генерации и на новых семействах,
с повторениями и учётом цены дополнительного входа.
